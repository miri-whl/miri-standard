## 2. The finding survives its own fix

The Packaging Baseline is **still constant across all five wheels** — 2 of 2,
every time. That was the observation the whole exchange started from, and
gating did not remove it. What gating changed is its price: the same
uninformative constant went from 8% of a fixed 100, to ~14% under
renormalization alone, to **3.6%** now.

That seems worth stating plainly because it is the honest read: §3 did not
make the Baseline informative. It made it cheap. Whether two SHOULD checks
that every correctly built wheel earns should be scored at all is a separate
question we are not reopening.

The section view, corrected, also confirms a claim we made in the addendum
and could not then measure — that Deprecation & Lifecycle's problem was never
its score but how much of it was in play:

| Section | Under 0.4.0 | Under 0.5.0 |
|---|---|---|
| Deprecation & Lifecycle Coherence | 16 / 25 | **3 / 3** |

Twenty-two of those twenty-five points were never applicable to this artifact.
The old view asserted a denominator the score had already stopped using.

## 3. What we did not predict

**No posture yields a band.** We predicted miri-py at 100% and got exactly
that, but 100% of 55 with `grade: undetermined`. `MIRI-PY-015`, `036` and
`040` are MUST-level, require `execution`, and are not conditional, so any run
without execution forfeits three MUSTs. Your changelog names this and calls it
correct; we are recording that it surprised us anyway. We had modelled the
score and not the verdict.

Nor does full capability settle it. With `--execute --network`, `MIRI-PY-030`
still forfeits — it needs `previous-release`, and miri-py is unpublished — so
the grade stays `undetermined` at every capability level we can reach. Our own
README now leads with "100% of 55, undetermined" rather than a band.

**More capability lowers the score — and then settles the grade.** The
ladder, measured with the precedence rule implemented:

| Run | Score | Grade | Excluded | Forfeited |
|---|---|---|---:|---:|
| default (offline) | 100% of 55 | undetermined | 9 | 8 |
| `--network` | 95% of 59 | undetermined | 11 | 3 |
| `--execute` | 100% of 64 | undetermined | 9 | 5 |
| `--execute --network` | **96% of 68** | **gold** | 11 | 0 |

`--network` costs three points because it reveals two SHOULD failures — `005`
(PEP 740 attestations, which only a publish produces) and `027` (a
`SECURITY.md` URL needing a public repository) — that a capability-less run
could only forfeit. This is the model working, and it is counter-intuitive
enough to be worth a sentence somewhere: **asking for more evidence can lower
a score, because a forfeit is not a failure but can become one.** A publisher
who reads "run with more capabilities" as "score higher" will be surprised
once.

The last row is the precedence rule paying for itself. A networked run asks
the index whether miri-py has a prior release, is told it has none, and
therefore **excludes** `MIRI-PY-030` and `034` rather than forfeiting them —
the obligation never existed for a first release. Without the network the
same two checks forfeit. Identical arithmetic, different claim, and the
difference is the whole grade: `undetermined` becomes `gold`.

## 4. What implementing it found in our own scorer

Three things, all of the shape this exchange has been about.

**The guard we promised you would catch `scoring` would not have.** We wrote:
*"a test asserts our model declares every field each family's check schema
declares, so a re-pin carrying `scoring` fails loudly rather than dropping
it."* That test reads the schema from a path pinned to `check-v1.json`. v1
does not declare `scoring`, so it would have compared our model against a
schema that no longer describes the corpus, and passed clean.

What actually caught the re-pin was the sync script, which validates the
fetched corpus before writing: 57 definitions rejected, nothing written,
`'$schema', 'scoring' were unexpected` named explicitly on 001–003. The
protection held; the mechanism we described was not the one that held it. The
`$schema` bump is what made it loud, exactly as your §2 says.

**The same guard had a second hole.** Fixing the schema path exposed it:
the test compared schema keys against `model_fields`, so a field declared with
a pydantic alias — `schema_url` aliased to `$schema` — read as *unread* while
the model read it perfectly well. Left alone it would have false-negatived
every future aliased key. It now compares against validation aliases.

**Our section scores were still doing 0.4.0 arithmetic after the headline
moved.** This is the trap your changelog names:

> a linter that adds the fields and does not change its *arithmetic*
> validates clean and reports wrong numbers

We changed the conformance score, added the three required fields, validated
against `lint-report-v1`, and shipped a section view still awarding weight to
not-applicable checks. The report was schema-valid and internally
contradictory: a headline computed over 55 points beside a section table
summing to 100. Nothing in any schema relates the two, so nothing caught it —
we found it by re-running the five wheels and reading a section denominator
that did not match.

The countermeasure we have adopted is a test that derives the denominator, the
numerator and every count independently from the outcomes and compares them to
what the report publishes, across four capability postures. We would suggest
it as the shape of the guard the changelog says cannot exist in a schema: not
*"are the fields present"* but *"do the fields equal what the arithmetic
used"*.

## 5. Three of our own fixtures were shaped to the weak rules

`api_index: {}`, `patterns: []`, and a manifest indexing nothing — all three
now fail, which is the §2 fix working. They are our fixtures, they were
written before we reported the vacuity, and they had been shaped to the rule
as it then was. We mention it because it is the same failure mode in the same
week from the reporting side: a test written against a weak check encodes the
weakness and then defends it.

## 6. What is not done

Two gaps, named rather than glossed:

- **`MIRI-CONSUMER-052` is unimplemented.** Our conformance map reads consumer
  17/18 with one unpinned MUST. The `package.replaced` trigger is new work and
  we have not started it.

- **`MIRI-PY-005` reports a failure where it should report a forfeit.** Found
  while implementing the precedence rule. 005 is dual-flagged, so the rule
  says its implementation should evaluate the condition before a missing
  `network` becomes a forfeit — but run without the network our implementation
  returns FAILED, not skipped. It would fail an artifact for something nobody
  checked. Our runner currently gates 005 before the implementation sees it,
  which hides the defect rather than fixing it; the other four dual-flagged
  checks are now handed over and decide correctly. This is ours to fix, not a
  finding about the standard, but it is the same shape as everything else in
  this exchange: a check that answers confidently about evidence it does not
  have.

The precedence rule is now implemented and the caveat we were going to attach
to the `--execute --network` figure is withdrawn — that row is settled, not a
floor. `MIRI-CONSUMER-052` remains untouched.
